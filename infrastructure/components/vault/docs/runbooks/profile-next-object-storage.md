# Profile-Next Object Storage

`profile-next` lets users upload an avatar or banner straight to an S3-compatible object store with a short-lived signed address. The service never receives the file. When the client says the upload is done, the service reads the first bytes of the stored file, checks them, and only then makes the file the profile's image. This runbook covers what must exist on the storage side, how the service gets its credentials, and the checks that prove the setup is correct.

Nothing here is automated by the service. Run it when the bucket is first created and again after any bucket change.

## One bucket, immutable keys

| Item | Value |
|---|---|
| Purpose | every profile image, current or waiting to be confirmed |
| Name | `chatter-media` (add a per-environment suffix) |
| Public read | **Yes**, only through the CDN hostname |
| Writers | clients holding a signed PUT address; the service key |
| Versioning | **off** |
| Lifecycle rules | **none on the `profiles/` prefix** (see the warning below) |
| CORS | `PUT` from the web app origin(s); allowed headers listed explicitly (`Content-Type`, `Content-Length`, `If-None-Match`); `ExposeHeaders: ETag`; max age 3600 |

Key shape (built only by the service, never from request text):

```
profiles/{userId}/{avatar|banner}/{imageId}
```

`imageId` is a time-ordered UUID generated by the service for every upload. A key is never overwritten on purpose, so a public address never changes meaning and can be cached for good. Public address of an image: `{public-base-url}/profiles/{userId}/{avatar|banner}/{imageId}`. A replaced image is simply a new address.

> **Do not add an expiry rule to this bucket.** Live images and unconfirmed uploads share the `profiles/` prefix. Unconfirmed uploads, replaced images and refused files are deleted by the service itself (the sweeper, driven by the `pending_upload` table). A bucket-wide or prefix-wide expiry rule would delete live images.

### Service key permissions (least privilege)

| Permission | Why |
|---|---|
| `s3:PutObject` | a signed address is only as powerful as the key that signed it |
| `s3:GetObject` | reading the first bytes of an upload to check it |
| `s3:DeleteObject` | removing replaced, refused and abandoned files |

No bucket-admin rights and no `s3:ListBucket`: the service never lists. Browsers never hold any key.

## Settings

Set in `services/profile-next/profilenext-start/src/main/resources/application.yml` under `profile-next.images`, with environment overrides.

| Setting | Environment variable | Meaning | Default |
|---|---|---|---|
| `endpoint` | `PROFILE_NEXT_STORAGE_ENDPOINT` | S3 endpoint; blank uses the SDK default for AWS S3 | blank |
| `region` | `PROFILE_NEXT_STORAGE_REGION` | signing region (`auto` for Cloudflare R2) | `auto` |
| `path-style` | `PROFILE_NEXT_STORAGE_PATH_STYLE` | path-style addressing (needed by most emulators) | `false` |
| `bucket` | `PROFILE_NEXT_STORAGE_BUCKET` | the one bucket | none |
| `public-base-url` | `PROFILE_NEXT_PUBLIC_BASE_URL` | public CDN address of the bucket | none |
| `ticket-lifetime` | | how long a signed upload address stays valid | `PT5M` |
| `grace` | | how long after a ticket expires its key is still left alone by the sweeper | `PT10M` |
| `max-bytes.avatar` / `.banner` | | largest accepted file | 5 MB / 10 MB |
| `max-dimension.avatar` / `.banner` | | largest accepted width or height in pixels | 1024 / 2048 |
| `allowed-formats` | | accepted formats | `jpg, png, webp` |
| `inspect-bytes` | | bytes read from the start of an upload to tell what it is | 512 KiB |
| `sweep.interval` | | how often the sweeper runs | `PT1M` |
| `sweep.batch-size` | | keys handled per run | `100` |
| `sweep.retry-delay` | | wait before a failed delete is tried again | `PT5M` |
| `api-call-timeout` / `api-call-attempt-timeout` | | storage call time limits | 5 s / 3 s |

## Credentials in Vault

The service reads the credentials from `secret/profilenext` at startup.

| Vault key (either spelling works) | Value |
|---|---|
| `storage.access-key` or `storage.access_key` | access key id of the service key |
| `storage.secret-key` or `storage.secret_key` | secret access key of the service key |

`configure-secrets.sh` writes the underscore spelling (it turns the first `_` after the service prefix into a dot and keeps the rest). The service accepts both.

### Store the credentials

Vault must be running and unsealed ([bootstrap](bootstrap.md)).

Set `PROFILENEXT_STORAGE_ACCESS_KEY` and `PROFILENEXT_STORAGE_SECRET_KEY` in `infrastructure/components/vault/.env` (gitignored; the committed `.env.example` only lists the names), then push them:

```bash
infrastructure/components/vault/scripts/configure-secrets.sh profilenext
```

The script refuses to run while either is empty or a placeholder. To update just these keys without touching the rest of the secret (`VAULT_ADDR` and `VAULT_TOKEN` as in [bootstrap](bootstrap.md)):

```bash
vault kv patch secret/profilenext \
  storage.access-key="<access key id>" \
  storage.secret-key="<secret access key>"
```

### Verify without printing the values

```bash
vault kv get -format=json secret/profilenext | jq '.data.data | keys'
```

Expect the two `storage.*` key names. Do not print the values; `jq 'keys'` shows names only.

| Variable | Used for | Default |
|---|---|---|
| `VAULT_TOKEN` | token that can read `secret/profilenext` and `secret/common/jwt/rs256` | none |
| `VAULT_SCHEME`, `VAULT_HOST`, `VAULT_PORT` | where Vault is | `http`, `localhost`, `5002` |
| `PROFILE_NEXT_DB_URL`, `PROFILE_NEXT_DB_USERNAME`, `PROFILE_NEXT_DB_PASSWORD` | database | local development values |
| `PROFILE_NEXT_KAFKA_BOOTSTRAP_SERVERS` | Kafka | `localhost:5003` |
| `PROFILE_NEXT_STORAGE_BUCKET`, `PROFILE_NEXT_PUBLIC_BASE_URL` (and the endpoint, region, path-style variables above) | storage | blank |

Run the service:

```bash
export VAULT_TOKEN=<token>
cd services/profile-next && ./mvnw -pl profilenext-start spring-boot:run
```

Without storage credentials the service still starts. Reads and text edits work; requesting an upload ticket answers `503 service_unavailable` until the credentials are present.

## CORS rule

Browsers upload with a `PUT` from the web application's origin, so the bucket needs a CORS rule. List the allowed headers explicitly; a wildcard is rejected by some providers. Replace the origin with the real web origin(s).

```json
{
  "CORSRules": [
    {
      "AllowedOrigins": ["https://app.example.com"],
      "AllowedMethods": ["PUT"],
      "AllowedHeaders": ["Content-Type", "Content-Length", "If-None-Match"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3600
    }
  ]
}
```

Apply it:

```bash
aws s3api put-bucket-cors --bucket <bucket> --endpoint-url <endpoint> --cors-configuration file://cors.json
```

Reads go through the CDN, which needs its own CORS or no CORS at all depending on how the web app loads images.

## How orphans are prevented

The service, not the bucket, owns clean-up. Every key the service authorizes (a ticket) or retires (a replaced, removed, refused image, or a deleted account) has a row in `pending_upload` until the key is deleted or becomes the current image. The sweeper deletes keys whose time has come, and retries a failed delete until it works. So an abandoned upload lives at most `ticket-lifetime + grace + sweep interval` (15 to 16 minutes with the defaults).

What the service cannot see: objects written into the bucket by something other than a ticket it issued, and live images deleted by hand in the console (the profile would then point at a missing file). Neither is expected.

## Provisioning checks (run once per bucket)

Commands use the AWS CLI v2 with `--endpoint-url`, so the same lines work against S3, R2 and emulators. Below, `B` is the bucket and `E` the endpoint URL.

| # | Check | How | If it fails |
|---|---|---|---|
| C-1 | The bucket has no lifecycle rule and versioning is off | `aws s3api get-bucket-lifecycle-configuration --bucket B --endpoint-url E` answers "no such lifecycle configuration"; `aws s3api get-bucket-versioning --bucket B --endpoint-url E` shows no `Status` or `Suspended` | remove the rule / suspend versioning, otherwise live images can be deleted |
| C-2 | A signed PUT works with the signed headers | request a ticket through the service (`POST /api/v1/profiles/@me/images/avatar/upload`), then `curl -X PUT -H 'Content-Type: image/webp' -H 'Content-Length: <n>' -H 'If-None-Match: *' --data-binary @file '<uploadUrl>'` returns 200 | provider unusable; use AWS S3 |
| C-3 | A second PUT to the same address is refused | repeat C-2 with the same address; expect 412 | informational: the provider does not enforce the no-overwrite condition. The short ticket lifetime is then the only limit on replacing a file after it was checked |
| C-4 | A signed PUT rejects a different `Content-Type` or length | repeat C-2 with a wrong header; expect 403 | informational: the commit re-checks type and size, so a file that slips through is still refused |
| C-5 | Browser preflight is answered | `curl -i -X OPTIONS -H 'Origin: <web origin>' -H 'Access-Control-Request-Method: PUT' -H 'Access-Control-Request-Headers: content-type,if-none-match' '<uploadUrl>'` returns the matching `Access-Control-Allow-*` headers | fix the CORS rule (list headers explicitly) |
| C-6 | Ranged read works and deleting a missing key succeeds | `aws s3api get-object --bucket B --key <key> --range bytes=0-1023 /dev/null --endpoint-url E`; `aws s3api delete-object --bucket B --key does-not-exist --endpoint-url E` returns success | provider unusable |
| C-7 | The CDN serves the bucket and caches extensionless keys | `curl -sI '<public-base-url>/profiles/<userId>/avatar/<imageId>'` returns 200 with the stored `Content-Type`; a repeat request shows a cache hit header (`cf-cache-status: HIT` or `X-Cache: Hit`) | add a cache rule that caches regardless of extension |

The same behaviours (C-2, C-3, ranged reads, delete) are proven against an S3-compatible emulator by `SdkObjectStoreClientContractTest` in the repository's test suite; the checks above prove them against the real provider.
