# Profile image upload: design draft (pending-upload ledger)

Status: IMPLEMENTED. Supersedes the earlier Cloudinary-promotion design (`IMAGE_REDESIGN_SPEC.md` and the `specs/012`, `014`, `015` image parts). Section 10 lists where the code differs from the text below.

## 1. Goals

- Users upload avatar and banner **directly to object storage** through a presigned ticket.
- The workflow is **pluggable** across providers (S3, GCS, Azure, Cloudinary, ...).
- **Domain logic is separate from infrastructure.** Domain is pure Java with no IO.
- Focus: **no orphan files** and **consistency** between the DB and object storage.
- Each profile has exactly 2 image slots: `AVATAR` and `BANNER`.
- Not over-engineered.

Out of scope for now: rate limiting, thumbnails/variants (handled later by `ImageUrlResolver`), private/signed reads, auditing of out-of-band deletions.

## 2. Core ideas

1. **Immutable keys.** Every upload gets a new key `profiles/{userId}/{slot}/{imageId}` (`imageId` is a UUIDv7 generated by the backend). A key is never overwritten by design.
2. **The DB pointer is the commit point.** `profile.avatar_image_id` / `profile.banner_image_id` change only in a DB transaction after validation.
3. **A ledger of keys.** `pending_upload` holds a row for every key we authorize or retire, until it is deleted or becomes current. The sweeper deletes exact keys, so no provider `list` is needed.
4. **Intent before side effect.** Any destructive storage call is preceded by a committed DB row recording the intent.
5. **Idempotent deletes.** Deleting a missing object counts as success, so every retry is safe.

## 3. Schema

`profile` (metadata is merged here; there is no separate image metadata table):

```sql
-- replaces avatar_public_id / avatar_url / banner_public_id / banner_url
avatar_image_id uuid NULL,
banner_image_id uuid NULL
```

URLs are derived through `ImageUrlResolver`, not stored.

```sql
CREATE TABLE pending_upload (
    image_id     uuid PRIMARY KEY,
    user_id      bigint      NOT NULL,
    slot         text        NOT NULL,   -- 'AVATAR' | 'BANNER'
    state        text        NOT NULL,   -- 'PENDING' | 'DISCARD'
    expires_at   timestamptz NULL,       -- ticket expiry; PENDING only
    delete_after timestamptz NOT NULL,   -- PENDING: expires_at + grace; DISCARD: now
    created_at   timestamptz NOT NULL
);
CREATE UNIQUE INDEX pending_upload_one_per_slot
    ON pending_upload (user_id, slot) WHERE state = 'PENDING';
CREATE INDEX pending_upload_due_idx ON pending_upload (delete_after);
```

- `pending_image_removal` is dropped.
- Row lifecycle: `PENDING` -> (commit) row deleted, key is current. A replaced or removed image gets a `DISCARD` row. A rejected or abandoned upload ends as `DISCARD` or expires. The sweeper deletes the object, then the row.

## 4. Layering

### Domain (pure, no IO)

- `Profile`: `replaceImage(slot, imageId)` returning the previous id, `removeImage(slot)`.
- `ImageSlot` (`AVATAR`, `BANNER`) and `ImagePolicy`: `check(slot, contentType, declaredSize)` and `checkStored(slot, ObjectInfo)`.
- `ImageSniffer.detect(bytes)`: magic-byte format detection (JPEG, PNG, WebP, ...).
- `ObjectKeys.of(userId, slot, imageId)`.
- `PendingUpload` state transitions: `issue`, `reuseIfActive`, `discard`, `isDue(now)`.

### Application

Use cases: `RequestImageUpload`, `CommitImageUpload`, `RemoveImage`, `DeleteProfile`, `SweepPendingUploads`.
Ports: `ObjectStoragePort`, `ImageUrlResolver`, `ProfileRepository`, `PendingUploadRepository`, `Clock`, `ImageIdGenerator`.

### Infrastructure

`S3ObjectStorage`, `CloudinaryObjectStorage` (and other providers), JPA repositories, the scheduled sweeper, an in-memory fake storage for tests.

## 5. Object storage port

```java
interface ObjectStoragePort {
    UploadTicket issueUpload(ObjectKey key, UploadConstraints c, Duration ttl);
    Optional<ObjectInfo> stat(ObjectKey key);                    // size, contentType, lastModified (+ etag)
    byte[] readHeader(ObjectKey key, int bytes);                 // ranged read of the first N bytes
    void delete(ObjectKey key);                                  // idempotent: missing == success
}
interface ImageUrlResolver { URI urlFor(ObjectKey key); }
```

- `UploadTicket` = `{method, url, fields, headers, expiresAt}`. It covers S3 POST policy, S3/GCS PUT and Cloudinary signed upload.
- `UploadConstraints` = content type, max size, no-overwrite. These are best-effort and provider-dependent (S3 presigned PUT cannot enforce size). **The commit-time checks are the real guard.**
- Capability flag per provider, e.g. `validatesOnUpload` (Cloudinary), allowing the header sniff to be skipped.

## 6. Workflows

### 6.1 Request ticket: `POST /images/{slot}/ticket {contentType, size}`

- Domain check: `ImagePolicy.check(slot, contentType, size)`. On failure return 422.
- Look up the `PENDING` row for `(userId, slot)`:
  - exists and not expired: reuse its `imageId`;
  - otherwise insert a row (new `imageId`, `PENDING`, `expires_at = now + ttl`, `delete_after = expires_at + grace`).
- The partial unique index enforces at most one `PENDING` row per slot, even under concurrency.
- No `profile` row is required yet.
- Commit the transaction, **then** call `issueUpload(key, constraints, ttl)`. Return `{imageId, ticket}`.

### 6.2 Upload

- The client uploads straight to storage using the ticket. The backend is not involved. Retries hit the same key because the `imageId` is reused.

### 6.3 Commit: `POST /images/{slot}/commit {imageId}`

All provider calls happen first, with no lock and no DB transaction. The DB flip comes last.

**3.1 DB checks**
- `imageId` equals the slot's current id: return 200 (idempotent retry).
- No `PENDING` row for `(userId, imageId)`: 409.
- Row expired: 410 (the client requests a new ticket).

**3.2 Existence and metadata**
- `stat(key)`. Missing: 409 and keep the row so the client can finish the upload and retry.
- Transient provider error (timeout, 5xx): return 503. Never treat an error as "invalid" and never delete.
- `ImagePolicy.checkStored(slot, info)` checks the actual size and content type.

**3.3 Header sniff**
- `readHeader(key, 16)`, then `ImageSniffer.detect(bytes)`.
- The detected format must be allowed for the slot and match the declared content type. Mismatch goes to the reject path.
- Skipped when the provider declares `validatesOnUpload`.

**3.4 Accept (one short DB transaction)**
- Lock the `PENDING` row with `SELECT ... FOR UPDATE`. If it is gone: 409.
- Delete that row (the key is now current and needs no ledger entry).
- Upsert `profile` and set the slot's current image id. This yields `previous`.
- If `previous` is non-null, insert a `DISCARD` row for it with `delete_after = now`.
- Commit.

**3.5 After commit (best-effort)**
- If `previous` is non-null: `delete(key(previous))`, then remove its `DISCARD` row.
- On any failure do nothing; the sweeper retries.
- Return 200 with `urlFor(key)`.

**3.6 Reject path (a check in 3.2 or 3.3 failed)**
- In one transaction, flip the row to `DISCARD` with `delete_after = now`.
- Then try to delete the object immediately.
- Return 422 with the reason. The client must request a new ticket.

### 6.4 Sweeper (scheduled)

- Select due rows: `WHERE delete_after <= now() ORDER BY delete_after LIMIT n FOR UPDATE SKIP LOCKED`.
- For each row, in its own transaction: `storage.delete(key)` (missing = success), then delete the row.
- On storage failure, roll back that row's transaction. It is retried on the next tick.
- Batch size is configurable. There is no `list` call and no prefix scan; the cost scales with due rows only.

### 6.5 Remove image

- One transaction: null the slot pointer, insert a `DISCARD` row for the old id.
- Post-commit delete and sweeper as in 6.3 step 3.5.

### 6.6 Account deletion

- One transaction:
  - insert `DISCARD` rows for both current images;
  - flip any `PENDING` rows to `delete_after = expires_at + grace`;
  - delete the `profile` row.
- The sweeper deletes everything on schedule. Ledger rows are independent of `profile`, so in-flight tickets are still cleaned up.

## 7. Failure analysis (step 6.3 and neighbours)

Ordering rules: everything before 3.4 is read-only; one DB transaction makes the change visible; DB intent is written before any destructive storage call; deletes are idempotent.

| Failure point | State left behind | Recovery | User impact |
|---|---|---|---|
| Crash or error in 3.1 to 3.3 | Nothing changed; `PENDING` row and object remain | Client retries; otherwise the sweeper deletes after `expires_at + grace` | None |
| `stat`/`readHeader` timeout or 5xx | Same as above | Client retries | 503 |
| 3.4 transaction fails | Nothing changed | Client retries | 5xx |
| Crash after 3.4 commit, before response | Pointer flipped; `DISCARD` row for previous exists | Retry hits "already current" and gets 200; sweeper deletes previous | None |
| Crash after 3.4 commit, before 3.5 delete | `DISCARD` row exists | Sweeper | None |
| 3.5 delete done, `DISCARD` row removal failed | Stale row, object already gone | Sweeper retries; "not found" = success; removes the row | None |
| 3.6 crash between `DISCARD` write and delete | `DISCARD` row exists | Sweeper | None |
| Ticket step: row committed, `issueUpload` or client fails | Row exists, no object | Sweeper deletes a non-existent key (no-op) | None |

Why order matters: if a ticket were issued before its row was written, a crash would leave an untracked object. So step 6.1 commits the row first.

## 8. Invariants

- **I1:** The profile pointer never references an unvalidated object. The flip happens only after validation.
- **I2:** A key referenced by the pointer is never touched by the sweeper. Its `PENDING` row is removed in the same transaction as the flip, and `DISCARD` rows are created only for keys the pointer has moved off.
- **I3:** Every key the service authorizes has a ledger row until it is deleted or becomes current. A bad or abandoned object lives at most `ttl + grace + sweep interval`.
- **I4:** Commit and the sweeper never act on the same row at once (`FOR UPDATE` versus `SKIP LOCKED`). Commit also rejects expired rows, and the sweeper only acts after `expires_at + grace`.

## 9. Known gaps and open items

- **Overwrite after validation:** within the ticket TTL a user could overwrite a key after it passes the header sniff. Mitigations: short TTL (~5 min), no-overwrite constraint (S3 `If-None-Match: *`, Cloudinary `overwrite=false`). Optional stronger fix: pin the ETag from `stat` and send `If-Match` on `readHeader`. **Resolved, see section 10.**
- **Untracked objects:** objects created without a ledger row (bugs, manual uploads) are never found. Accepted for now.
- **Out-of-band deletion** of a live object leaves a dangling pointer. Out of scope.
- **Sweeper retries forever** on a permanently failing key. Options: log an error after N attempts, or accept. **Resolved, see section 10.**
- **Header sniff on every provider**, or skip where the provider validates on upload (Cloudinary)? **Resolved, see section 10.**
- Reads assumed public via CDN.
- **No rate limiting.** The one-pending-per-slot rule caps unconfirmed uploads at 2 per user, but it is not a rate limit.

## 10. As implemented (differences from the text above)

- **Port name and shape:** the port is `ImageStorage` (the repository's naming), taking an `OwnedImage` (user, slot, image id). Core owns the key layout in `ImagePath` (`profiles/{userId}/{slot}/{imageId}`); the S3 adapter uses it as the object key and the presentation layer prepends the public base URL. There is no separate `ObjectKeys`.
- **Header read:** `readHeader` reads `inspect-bytes` (default 512 KiB, enough for a JPEG whose metadata comes before the frame header), not 16 bytes. It is skipped when the adapter's `validatesOnUpload()` is true (the S3 adapter answers false).
- **No overwrite (resolved):** the signed ticket carries `If-None-Match: *`; the ticket lives 5 minutes. ETag pinning was not added. The S3-emulator contract test shows both the no-overwrite condition and signed-header enforcement hold on that provider; on a provider that ignores them, the commit's own checks and the short ticket lifetime remain.
- **Sweeper failures (resolved):** a failed delete is not retried in place. The row's `delete_after` moves forward by `sweep.retry-delay` (default 5 minutes), so one stubborn key cannot hold up the rows behind it; it is retried forever and logged at error level on every failure. There are no attempt counters.
- **Header sniff (resolved):** sniff unless the provider validates on upload.
- **Reuse window:** a pending ticket is handed out again only while at least 30 seconds are left (`PendingUpload.MIN_REUSE_WINDOW`); otherwise it is retired (keeping its sweep time) and a new one starts. The response's `expiresAt` is the ledger's, because that is the expiry commit enforces.
- **Commit race:** two simultaneous commits of one ticket: the loser finds the ticket gone, sees the slot already holds the image, and answers `already_applied`.
- **HTTP mapping:** unknown or already used ticket: 404 `not_found`; expired: 410 `upload_expired`; file not there yet: 409 `upload_incomplete`; lost race for a new ticket: 409 `conflict`; every file rule (format, size, dimensions, unreadable, type mismatch): 422 `image_rejected` with a fixed sentence per rule.
- **Endpoints:** `POST /api/v1/profiles/@me/images/{avatar|banner}/upload` (body `contentType`, `sizeBytes`), `POST .../commit` (body `imageId`), `DELETE .../{avatar|banner}`. The old Cloudinary webhook endpoint is gone.
- **Schema:** migration `V2__image_upload_ledger.sql` replaces the old `*_public_id` / `*_url` columns with `avatar_image_id` / `banner_image_id` and drops `pending_image_removal`. Old image references belonged to another provider and are not carried over. `pending_upload.created_at` is set by the database.
- **Account deletion:** the notice handler writes `DISCARD` rows for both current images, turns every pending ticket into a `DISCARD` row keeping its sweep time, and deletes the profile row, in one transaction. A late commit then finds no pending ticket (404).
- **Scheduling:** `@EnableScheduling` was missing in the service, so no scheduled job could run; it now sits on `ImageMaintenanceScheduler`.
