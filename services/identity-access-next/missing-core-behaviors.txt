IDENTITY-ACCESS-NEXT (IAN) IDENTITYACCESS-CORE IMPLEMENTATION GUIDE
============================================

Purpose
-------
This is a short AI handoff for completing identityaccess-core without copying IA's DDD
structure. For a focused session, read "Shared rules" and only the selected capability:

1. user
2. emailverification
3. authentication

See infrastructure-structure-design.txt only when implementing infrastructure adapters.


Shared rules
------------
- Organize by capability, not by token type. Do not create a generic token package.
- Command and query contracts belong in core; datastore implementations belong in
  infrastructure.
- Use command/ and query/ only for public use cases. Keep models and ports under
  internal/model and internal/port.
- Core ports are plain Java interfaces and must not name Redis, JDBC, JWT, SMTP, or
  another implementation technology.
- JWT is infrastructure. Core exposes AccessTokenIssuer.issue(...) -> String only.
- Temporary data can still be a core concept. Core owns lifecycle rules; infrastructure
  owns storage and serialization.
- Messaging was removed. Preserve its business effects through direct synchronous use-
  case coordination; do not restore domain/integration event infrastructure.
- Avoid aggregate base classes, shared kernels, and domain services without concrete
  behavior.

Target core packages
--------------------

com.minewaku.chatter.identityaccess/
|-- user/
|   |-- command/
|   |-- query/
|   `-- internal/{application,model,port}/
|-- emailverification/
|   |-- command/
|   `-- internal/{application,model,port}/
|-- authentication/
|   |-- command/
|   |-- query/
|   `-- internal/{application,model,port}/
`-- shared/handler/


PART 1: USER
============

Already implemented
-------------------
- Register user.
- Find user by ID/email.
- Enable/disable, lock/unlock, activate-after-verification, and soft-delete.
- UserAccount and its email, username, birthday, password, ID, and status values.
- UserAccountRepository, UserIdGenerator, and hash-only PasswordHasher ports.

Required changes
----------------

1. Replace account status semantics with:

   PENDING_VERIFICATION -> ACTIVE       only after valid email verification
   ACTIVE -> LOCKED -> ACTIVE           security lock/unlock
   ACTIVE -> SUSPENDED -> ACTIVE        admin suspend/reinstate
   any non-deleted state -> DELETED

   Never allow a pending account to become active through unlock/reinstate. Rename:

   DisableUserAccountUseCase -> SuspendUserAccountUseCase
   EnableUserAccountUseCase  -> ReinstateUserAccountUseCase

2. Extend PasswordHasher:

   hash(PlainPassword) -> PasswordHash
   matches(PlainPassword, PasswordHash) -> boolean

3. Add change password:

   ChangePasswordUseCase.Command(long userId, String currentPassword,
                                  String newPassword)
   -> Result(boolean changed)

   Require an accessible account, correct current password, and a different new
   password. Add passwordModifiedAt only if retaining IA's five-minute change interval.

4. Preserve registration outcomes internally:

   Registered(long userId) | AccountAlreadyActive | VerificationPending

5. Separate CQS repositories when persistence work begins:

   UserAccountRepository       -> write/domain model
   UserAccountViewRepository   -> query projections

   Existing FindUser queries may remain, but should use the read port and immutable
   query results after that split.

Cross-capability effects
------------------------
- Successful registration must request email verification.
- Soft deletion must revoke all refresh sessions for that user.
- Email change, if implemented, returns the account to PENDING_VERIFICATION and requests
  new verification.

Optional/undecided
------------------
- ChangeUsernameUseCase(long userId, currentPassword, newUsername) -> changed.
- ChangeEmailUseCase(long userId, currentPassword, newEmail)
  -> changed + verificationRequired.
- Account restoration is not approved; deletion anonymizes identity and credentials.


PART 2: EMAILVERIFICATION
=========================

Current status
--------------
Not implemented in IAN. IA created verification data and sent mail through event
subscribers. Keep the effects, not the messaging mechanism.

Public commands
---------------

RequestEmailVerificationUseCase.Command(String email)
-> Accepted

- Public, rate-limited, and non-enumerating.
- Only a pending account is eligible.
- Replace the previous outstanding verification.
- Create a new verification and request delivery.

VerifyEmailUseCase.Command(String token)
-> Verified(long userId) | InvalidOrExpired | AlreadyVerified

- Resolve the opaque token.
- Reject missing, expired, or consumed verification.
- Mark it verified and perform PENDING_VERIFICATION -> ACTIVE.
- Do not expose activation by arbitrary user ID as a public endpoint.

Internal model
--------------

EmailVerification:
- verificationId/token reference
- userId
- email
- createdAt
- expiresAt
- verifiedAt

Rules: expiring, single-use, replaceable on resend, and valid only for a pending account.
Use EmailVerification, not VerificationToken or VerificationChallenge, as the model name.

Core ports
----------

EmailVerificationRepository:
- save(EmailVerification)
- findByPresentedToken(String) -> Optional<EmailVerification>
- invalidateForUser(UserId)

VerificationTokenGenerator:
- generate() -> String

VerificationNotifier:
- sendVerification(Email, String rawToken, Instant expiresAt) -> accepted/void

Infrastructure must hash stored tokens and owns Redis/JDBC, URL construction, templates,
and SMTP. PostgreSQL simplifies atomic activation; Redis gives natural expiry but no
normal transaction with a PostgreSQL account.


PART 3: AUTHENTICATION
======================

Current status
--------------
Not implemented in IAN. Password matching, login, access-token issuance, refresh
sessions, refresh, logout, and session queries are missing.

Public commands
---------------

AuthenticateUseCase.Command(String email, String password, DeviceInfo deviceInfo)
-> Authenticated(String accessToken, String refreshToken)

- Require an ACTIVE account and matching password.
- Create RefreshSession and return both credentials.

RefreshAccessTokenUseCase.Command(String refreshToken)
-> Refreshed(String accessToken)

- Use the same non-rotating refresh token.
- Require a non-revoked, non-expired session and ACTIVE account.
- Return only a new access token.

LogoutCurrentSessionUseCase.Command(String refreshToken)
-> Result(boolean revoked)

- Resolve and idempotently revoke the matching session.

Public query
------------

FindSessionsQuery.Command(long userId)
-> List<SessionView>

SessionView: sessionId, userId, deviceInfo, issuedAt, expiresAt, lastUsedAt, revokedAt.
Presentation obtains userId from the authenticated principal.

Internal model
--------------

RefreshSession:
- sessionId
- userId
- deviceInfo
- refreshTokenHash/reference
- issuedAt
- expiresAt
- lastUsedAt
- revokedAt

Rules: bounded lifetime, explicit revocation, and account accessibility. There is no
generation, rotation, grace period, or replay-detection algorithm.

Core ports
----------

RefreshSessionRepository:
- save(RefreshSession)
- findByPresentedToken(String) -> Optional<RefreshSession>
- findByUserId(UserId) -> List<RefreshSession>
- revokeAllByUserId(UserId) -> int

RefreshSessionViewRepository:
- findByUserId(UserId) -> List<SessionView>

RefreshTokenGenerator:
- generate() -> String

AccessTokenIssuer:
- issue(UserId, Email) -> String

Infrastructure implements opaque secure token generation, hashes stored refresh tokens,
and implements AccessTokenIssuer as JwtAccessTokenIssuer. JWT/Claims/key types must not
appear in core. Presentation owns the Secure/HttpOnly/SameSite cookie.

Optional/undecided
------------------
- LogoutSessionUseCase(userId, sessionId, currentPassword) -> revoked.
- LogoutOtherSessionsUseCase(userId, currentSessionId, currentPassword) -> revokedCount.


Recommended session order
-------------------------
1. USER: correct statuses and add PasswordHasher.matches/change password.
2. EMAILVERIFICATION: add model, ports, resend, verify, and registration integration.
3. AUTHENTICATION: add login, simplified refresh session, refresh, logout, and query.
4. USER + AUTHENTICATION: revoke sessions on password change, suspension, and deletion.
5. Add optional username/email/session-management behavior only after explicit approval.

Do not implement
----------------
- Refresh-token rotation, generations, grace periods, or AES refresh-token codec.
- JWT parsing/signing classes in core.
- Messaging/domain-event infrastructure.
- A generic token package.
- Account restoration without an approved retention/privacy design.
