IDENTITY-ACCESS-NEXT: EMAIL VERIFICATION (PART 2)
=================================================

Scope
-----
Implement email verification in identityaccess-core only. This file supersedes
older email-verification plan notes where they conflict. Part 1's successful
email-change behavior is included here. Do not implement endpoints, adapters,
rate limiting, storage technology, or mail templates in this task.

Structure
---------
- Use emailverification/command for public use cases and
  emailverification/internal/{application,model,port} for implementation.
- Core ports are plain Java interfaces without infrastructure technology names.
- Coordinate use cases directly and synchronously; add no messaging, events,
  generic token package, aggregate base, or public activation by user ID.

Public behavior
---------------
RequestEmailVerificationUseCase.Command(String email) -> Accepted
- For every valid email, return the same fieldless Accepted result, including
  absent, ineligible, and externally throttled accounts. Use the existing Email
  validation for malformed input. The outer layer owns rate limiting; core adds
  no limiter port or policy in this task.
- Only a PENDING_VERIFICATION account may receive a new token. Invalidate its
  previous outstanding token, create a replacement, and request delivery.

VerifyEmailUseCase.Command(String token)
  -> Verified(long userId) | InvalidOrExpired | AlreadyVerified
- Missing, invalidated, or expired tokens return InvalidOrExpired. A token
  expires when now >= expiresAt. Blank tokens are invalid.
- A consumed token returns AlreadyVerified until its expiry; retain enough
  state for this result. A resend invalidates the old token, so presenting it
  returns InvalidOrExpired.
- For an unused valid token, load the user and require both
  PENDING_VERIFICATION status and an email matching the verification record.
  Otherwise return InvalidOrExpired. Mark the verification used and transition
  the account to ACTIVE in one transaction; only then return Verified(userId).

Registration and email change
-----------------------------
- A newly registered pending account gets one verification and delivery request
  before registration returns. Existing-account results do not trigger delivery.
- On a successful change to a different email, change the account from ACTIVE
  to PENDING_VERIFICATION, invalidate previous outstanding verification, and
  request verification for the new email. Keep Part 1's
  changed/verificationRequired result. Unchanged or rejected changes do nothing.
- Pending accounts cannot use protected account changes; resend and verify
  remain available. Status or email changes before verification make an unused
  token invalid under the checks above.

Model and ports
---------------
- Name the model EmailVerification: raw token, userId, email, createdAt,
  expiresAt, and optional verifiedAt. It is expiring, single-use, and replaceable.
- Default lifetime: 24 hours, supplied as a configurable Duration. Use an
  injected Clock for creation and expiry checks.
- EmailVerificationRepository: save(EmailVerification),
  findByPresentedToken(String) -> Optional<EmailVerification>,
  invalidateForUser(UserId). The current contract permits storing raw tokens;
  do not log or include them in public results.
- VerificationTokenGenerator.generate() -> String. Its later adapter must
  produce an unpredictable token.
- VerificationNotifier.sendVerification(Email, String rawToken, Instant expiresAt)
  -> void. URL construction and delivery implementation belong outside core.
- Reuse USER's Email, UserId, UserAccount, and UserAccountRepository.

Transaction and verification expectations
-----------------------------------------
- Put @Transactional on command handlers coordinating account and verification
  writes. Propagate repository and notifier failures. Delivery accepted by a
  mail provider cannot be rolled back; a dead link after a later commit failure
  is an accepted limitation, recoverable by resend while the account is pending.
- Core tests cover creation, resend, expiry boundary, replay, invalidation,
  status/email mismatch, registration/email-change effects, and failure paths.
  Adapter tests later must prove database rollback and concurrent single-use;
  @Transactional alone does not guarantee the latter.
