# Identity Access - detailed structure plan

## 1. Goal and architectural position

Replace tactical DDD (aggregates, domain events, shared kernel, and a separate domain artifact) with a pragmatic Clean Architecture modular monolith.

Clean Architecture remains a dependency rule, not a requirement for DDD. The service will retain business rules and value objects, but it will not recreate DDD ceremony simply because a class has business meaning.

## 2. Physical Maven modules

Keep a small number of physical modules. Do not initially create a Maven artifact for every feature.

```text
identityaccess-parent
|- identityaccess-core
|- identityaccess-infrastructure
|- identityaccess-presentation
`- identityaccess-start
```

Dependency direction:

```text
presentation   -> core
infrastructure -> core
start          -> presentation + infrastructure
```

`identityaccess-core` replaces the old global `identityaccess-domain` plus `identityaccess-application` split. It is the only module that contains feature business logic. `identityaccess-infrastructure` supplies technical implementations and configuration. `identityaccess-presentation` contains HTTP concerns. `identityaccess-start` is the Spring Boot composition root.

## 3. Logical modules inside core

Organize core by feature, not by global technical layer.

```text
com.minewaku.chatter.identityaccess
|- user
|  |- public API types
|  `- internal
|     |- application
|     |- model
|     `- port
|- auth
|- session
|- verification
`- workflows
```

Each feature exposes a small, intentional API. Other features may use only that API, never another feature's `internal` model, repository, mapper, or persistence detail. `workflows` owns use cases that must coordinate two or more features.

Examples:

- `auth` calls `user`'s public authentication API in-process.
- `verification` calls `user`'s public activation API in-process.
- `workflows` disables an account and revokes its sessions in one transaction.

There are no queues or HTTP calls for these internal interactions. Do not create reciprocal dependencies: `user -> session` and `session -> user` is forbidden. The workflow module depends on both instead.

Use Spring Modulith/ArchUnit tests later to verify that only feature APIs are imported. This creates real logical boundaries without extra Maven-module overhead.

## 4. Core is deliberately persistence-aware

Use Spring Data JDBC models directly in `identityaccess-core`. Do not introduce `UserRow <-> UserAccount` mapping solely to obtain a framework-pure core.

Core is allowed to contain:

- Spring Data JDBC mapping annotations (`@Table`, `@Id`, `@Version`, `@Embedded`, etc.).
- Spring Data repository interfaces.
- Feature use cases, state-transition methods, ports, and optional Spring transaction annotations.

Infrastructure retains:

- datasource, transaction-manager, Spring Data JDBC, and `JdbcCustomConversions` configuration;
- PostgreSQL driver and Flyway migrations;
- Redis, JWT, password-hashing, mail, and other technical implementations.

Presentation retains controllers, HTTP request/response DTOs, web validation, and error-to-HTTP mapping.

This is an explicit trade-off: easier code and fewer mappings in exchange for a dependency on Spring Data. It has no material performance disadvantage. Database round trips, SQL, indexes, connection pooling, and result size dominate; do not select this design based on micro-allocation assumptions.

## 5. Model rules

Retain immutable value objects where they enforce a real invariant or express an important type:

- `UserId`, `Email`, `Username`, `Birthday`;
- `Password` only while validating input; never persist, log, or return it;
- `PasswordHash` for persisted algorithm/hash/salt data;
- an `AccountStatus` state representation instead of independent mutable `isDeleted`, `isLocked`, and `isEnabled` booleans.

Use Spring Data JDBC custom conversions for a value object stored in one column (`Email`, `UserId`, `Username`, and status). Use `@Embedded` only for a value that maps to multiple columns, such as `PasswordHash`.

Use optimistic locking (`@Version`) on mutable user and session records. Keep database-level constraints and indexes authoritative: normalized-email uniqueness, relevant non-null rules, and lookup indexes. Do not serialize persistence models directly as REST responses.

## 6. Account state and tokens

Identity Access is the sole authority for user accessibility. Other services receive a validated subject and scopes/roles, not canonical copies of mutable account flags.

- Issue short-lived access JWTs and rotate refresh tokens.
- On lock, disable, deletion, password change, or equivalent security invalidation, revoke sessions/refresh capability so no new access JWT can be minted.
- A previously issued self-contained access JWT remains usable until expiry unless the resource service performs an online revocation/state check.
- Where immediate revocation is required, use token introspection, a gateway, or a deny-list/state check. An asynchronous cache-invalidating event alone is eventually consistent and is insufficient for that guarantee.
- Do not include mutable account-state flags in JWT claims.

## 7. Events and outbox

Do not use events merely because the model changed. Local synchronous feature coordination uses direct calls.

Remove integration events and the outbox only if no external service requires a reliable asynchronous reaction. Retain a narrowly versioned integration event plus outbox when there is an actual contract, such as cross-service personal-data erasure, provisioning, or reliable downstream cache updates.

Reliable verification-email delivery is also a legitimate reason for a local outbox, even when no other business service consumes the event.

## 8. Future extraction rule

Do not split a feature into its own Maven artifact or microservice merely because it has a package. Extract only when ownership, deployment cadence, data ownership, operational needs, and failure boundaries genuinely justify it.

If a feature later becomes a Maven module, direct sibling dependencies are valid (`auth -> user`) but must form an acyclic graph. Keep the cross-feature workflow as the coordinator rather than introducing a cycle or prematurely adding a message broker.
